Salesforce Integration

Identity Verification
for Salesforce

Connect Incode's eKYB (electronic Know Your Business) platform to your Salesforce org. Trigger business verification, track results, and review session details — all without leaving Salesforce.

Lightning Web Components Apex Contact · Lead · Account eKYB / eKYC API v59.0+

1 Overview

The Incode Identity Verification for Salesforce package installs a full verification workflow directly into your CRM. Once configured, your team can initiate, monitor, and review business identity verifications from any Contact, Lead, or Account record page.

🚀
One-Click Requests
Send a verification email from any record with a single click. The email auto-populates from the record's contact details.
⚡
Real-Time Updates
Status updates automatically via webhook the moment a session completes — no manual refresh needed.
🔍
Full eKYB Output
View verified entity type, field-level results, applied business rules, UBOs, and directors with match indicators.
🌍
US & EU Support
Automatically adapts output structure for both US (people with titles) and EU (UBO/director verification results).

Supported Salesforce Objects

ObjectSupportedAuto-populated Fields
Contact✓Email, First Name
Lead✓Email, First Name
Account✓Account Name

Status Lifecycle

Pending Approved Declined Error

Status transitions from Pending once Incode fires a webhook. Approved means the verification passed your configured business rules. Declined means it did not pass. Error indicates an unexpected failure during the session.

2 How It Works

The integration bridges Salesforce and the Incode Omni Platform through outbound API calls and an inbound webhook endpoint.

1
User clicks "Request Verification"
The LWC component calls IncodeService.startSession() with the record ID, email address, and object type.
2
Session created via Incode API
Apex calls POST /omni/start → returns a session token and interview ID.
POST /omni/start
3
Hosted verification URL retrieved
Apex calls GET /omni/onboarding-url using the session token to obtain the unique verification link.
GET /omni/onboarding-url
4
Verification record created & email sent
An Incode_Verification__c record is inserted with status Pending. Salesforce sends the branded verification email to the contact.
5
Contact completes verification (out-of-band)
The contact opens the link on their device and completes the Incode-hosted verification flow.
6
Incode fires ONBOARDING_FINISHED webhook
The Incode platform POSTs to your Salesforce Site endpoint. IncodeWebhookHandler updates the verification record status and asynchronously fetches the score.
POST /incode/webhook → Salesforce Site
7
LWC reflects updated status
The component polls every 10 seconds, detects the status change, and fires a toast notification. The history row updates to Approved or Declined.

5 Configuration

Work through each sub-section in order. The total time is approximately 30–45 minutes.

5.1 — Named Credentials

Named Credentials store the Incode API base URLs. The package ships with two — one for each environment.

  1. 1

    Go to Setup → Named Credentials.

  2. 2

    Confirm both entries are present:

    Developer NameEndpointUsed when
    IncodeAPIhttps://demo-api.incodesmile.comUse Production API = unchecked
    IncodeAPI_Productionhttps://saas-api.incodesmile.comUse Production API = checked
ℹ️
No URL changes needed

The package selects the correct Named Credential at runtime based on the Use_Production_API__c checkbox in Custom Settings. You never need to edit the endpoint URLs.

5.2 — Custom Settings

This is the most critical configuration step. The package will not function without a valid API Key and Configuration ID.

  1. 1

    Go to Setup → Custom Settings → Incode Config → Manage.

  2. 2

    Click New in the Default Organization Level Value section.

  3. 3

    Fill in the following fields:

    FieldValueRequired
    API_Key__cYour Incode API KeyYes
    Configuration_ID__cYour Incode Configuration IDYes
    Admin_Email__cIncode admin user emailYes
    Admin_Password__cIncode admin user passwordYes
    Webhook_Secret__cHMAC signing secret (from Incode Dashboard)Recommended
    Use_Production_API__cLeave unchecked during initial setup—
  4. 4

    Click Save.

💡
Start with Demo

Always validate end-to-end in the Demo environment before checking the Use Production API box. Demo uses real Incode services with test credentials — no production data is affected.

5.3 — Activating the Webhook Site

The Incode platform needs a public HTTPS endpoint to deliver verification results back to Salesforce. This is handled by a Salesforce Site called IncodeWebhook.

  1. 1

    Go to Setup → Sites.

  2. 2

    Find IncodeWebhook. If status is Inactive, click Activate.

  3. 3

    Note your full webhook endpoint URL — you will need this in Section 6:

    https://<your-domain>.my.salesforce-sites.com/IncodeWebhook/services/apexrest/incode/webhook

5.4 — Assigning Permission Sets

Two permission sets are included. Both must be assigned correctly.

Incode_User — Salesforce users who request verifications

  1. 1

    Go to Setup → Permission Sets → Incode User → Manage Assignments → Add Assignments.

  2. 2

    Select the relevant users (sales team, operations, etc.) and click Assign.

Incode_Webhook_Guest — Site Guest User (required for webhooks)

🔴
Critical step

Without this assignment, incoming webhooks will fail silently. Verifications will stay Pending indefinitely even after the contact completes the flow.

  1. 1

    Go to Setup → Sites → IncodeWebhook → Public Access Settings.

  2. 2

    Click View Users → click the Guest User record (e.g., "Site Guest User, IncodeWebhook").

  3. 3

    Scroll to Permission Set Assignments → Edit Assignments. Move Incode Webhook Guest to Enabled. Click Save.

6 Webhook Registration

Register your Salesforce endpoint in the Incode Dashboard so the Incode platform knows where to deliver verification results.

  1. 1

    Log in to the Incode Dashboard and open your Configuration (the one whose ID you entered in Section 5.2).

  2. 2

    Navigate to the Webhooks section and click Add Webhook.

  3. 3

    Fill in the form:

    FieldValue
    URLYour Salesforce Site webhook URL from Section 5.3
    MethodPOST
    EventONBOARDING_FINISHED
    SecretThe value you entered in Webhook_Secret__c (if any)
  4. 4

    Click Save.

ℹ️
Why ONBOARDING_FINISHED?

This is the event Incode fires when a session ends — regardless of pass or fail result. Despite some versions of the API reference showing SESSION_SUCCEEDED, the actual event fired in both Demo and Production is ONBOARDING_FINISHED. The webhook handler normalises both variants.

  5. 5

8 Email Template Customization

When a verification is requested, Salesforce automatically sends a branded email containing the verification link. The default template is production-ready but can be customized.

  1. 1

    Go to Setup → Classic Email Templates → Incode Templates → Incode Verification Request.

  2. 2

    Click Edit and adjust the subject line, body text, or branding as needed.

  3. 3

    Click Save. Use Send Test and Verify Merge Fields to preview before going live.

🔴
Do not remove {!verificationUrl}

This merge field is replaced at send time with the unique Incode verification link. Removing or renaming it will result in emails with no actionable link.

  2. 2

10 Switching to Production

Once testing in Demo is successful, follow these steps to go live.

⚠️
Two credentials to update

The Demo and Production API Keys are different. You must update both the Custom Settings field and the IncodeAPI_Production Named Credential password. Missing either will cause authentication failures.

  1. 1

    Obtain your Production API Key from the Incode Dashboard.

  2. 2

    Go to Setup → Custom Settings → Incode Config → Manage → Edit. Update API_Key__c to the Production key and check Use Production API. Click Save.

  3. 3

    Go to Setup → Named Credentials → IncodeAPI_Production → Edit. Update the Password field with the Production API Key. Click Save.

  4. 4

    In the Incode Dashboard, register the webhook URL under your Production configuration (same steps as Section 6).

💡
Rolling back

To revert to Demo: uncheck Use Production API in Custom Settings and restore the Demo API Key. No redeployment is needed.

13 Security Model

Apex Sharing

ClassSharingReason
IncodeServicewith sharingStandard sharing rules apply to all record queries
IncodeEmailServicewith sharingRuns in logged-in user context
IncodeWebhookHandlerwithout sharingSite Guest User has no default access to custom objects; intentional and safe — handler only updates the specific record matching the incoming session ID

Webhook Signature Validation

When Webhook_Secret__c is populated, every inbound request is validated before any data is touched:

  1. Read the X-Incode-Signature header from the request.
  2. Compute HMAC-SHA256 of the raw request body using the stored secret.
  3. If signatures do not match → return HTTP 401. No data is changed.
💡
Strongly recommended for production

Webhook signature validation prevents unauthorized parties from sending forged status updates to your Salesforce org. Enable it by setting Webhook_Secret__c in Custom Settings and using the same value in the Incode Dashboard.

14 Troubleshooting

⚡

"Request Verification" shows an error immediately

Likely cause: Missing or incorrect API Key / Configuration ID in Custom Settings.

Go to Setup → Custom Settings → Incode Config → Manage → Edit. Verify API_Key__c and Configuration_ID__c contain no extra whitespace. Confirm the Use Production API checkbox matches your intended environment.

📧

Verification email is not received

Likely cause: Email deliverability restriction or spam filter.

Go to Setup → Email → Deliverability. Confirm Access Level is All Email. Check the recipient's spam folder. Use Send Test on the email template to confirm Salesforce can send from the org.

🔄

Status stays Pending after the contact completes the flow

Work through each check in order:

1. Site Active? — Setup → Sites → confirm IncodeWebhook shows Active.

2. Correct event registered? — Incode Dashboard → Configuration → Webhooks → confirm event is ONBOARDING_FINISHED.

3. Correct webhook URL? — Must end in /IncodeWebhook/services/apexrest/incode/webhook.

4. Guest User permission set? — Setup → Sites → IncodeWebhook → Public Access Settings → View Users → confirm Incode_Webhook_Guest is assigned.

5. Check Site History — Setup → Sites → IncodeWebhook → View Site History. Look for HTTP 4xx/5xx on incoming POST requests. 401 = secret mismatch. 403/500 = permission issue.

🔍

Session Details modal shows an error

Likely cause: Admin Email or Admin Password is missing or incorrect.

Go to Setup → Custom Settings → Incode Config → Manage → Edit. Verify Admin_Email__c and Admin_Password__c match the credentials you use to log in to the Incode Dashboard.

👁

Component is not visible on the record page

The component must be added via Lightning App Builder. Follow Section 7. Confirm you clicked Activate after saving and that the activation applies to the correct app/profile/record type combination.

🔒

Component shows a configuration error on load

The logged-in user does not have the Incode_User permission set. Assign it via Setup → Permission Sets → Incode User → Manage Assignments.

15 FAQ

Can multiple verification attempts be made for the same record?
Yes. Each click of "Request Verification" creates a new Incode_Verification__c record. The component shows the full history with the most recent attempt at the top, marked with a "latest" badge.
Does the component work with sandbox or developer orgs?
Yes. Use the Demo environment (leave Use Production API unchecked) and point the Incode Dashboard webhook at your sandbox Site URL.
What happens if the contact's email address is wrong?
The verification email will bounce or go undelivered. The Incode_Verification__c record will stay in Pending indefinitely. You can initiate a new verification request with the corrected email — the old Pending record will remain in the history.
Can verification emails be sent in languages other than English?
The email template can be edited to any language (Section 8). The Incode-hosted verification flow language is controlled by the language parameter in the session request, currently set to en-US. Contact Incode support if multi-language session flows are required.
Is personal data from the verification stored in Salesforce?
The Incode_Verification__c record stores status, score, timestamps, and a cached copy of the full session JSON (up to 128KB) for use in the detail view. No biometric data (ID document images, selfie photos) is stored in Salesforce.
Does this support Person Accounts?
Person Accounts are not explicitly supported in this version. The component targets standard Account records. Support for Person Accounts can be added in a future release.
How long does the verification link remain valid?
Session link validity is configured in the Incode Dashboard under the flow configuration. Contact your Incode account team to adjust the expiry window for your specific use case.
What Incode API endpoints does this integration use?
POST/omni/start Create a new verification session
GET/omni/onboarding-url Retrieve the hosted verification link
GET/omni/get/score Fetch verification score after completion
GET/omni/single-session Load full session details for the modal
POST/executive/log-in Authenticate admin to access session data
